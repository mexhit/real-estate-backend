# Filtering by Source rejects unknown values, unlike Capture creation's silent fallback

`docs/adr/0009-property-source-is-a-closed-set-defaulting-to-duashpi.md` chose a silent fallback to `duashpi` when a Capture is created with an unrecognized `source`, so a scraper's typo doesn't cost the listing. The new `GET /properties?sources=...` filter does the opposite: an unrecognized value in the `sources` query param is rejected outright (400), rather than silently ignored. These look inconsistent side by side but address different failure modes — ingestion leniency protects data from being lost to an upstream typo, while filter strictness protects an API caller from silently getting zero results because *their* typo matched nothing. Silently ignoring a bad filter value would look identical to "no properties match," which is a much worse failure to debug than a 400.

A related asymmetry: the frontend's Property Type filter options are a hardcoded constant, but Source's filter options are served from a new `GET /properties/sources` endpoint — the first metadata-list endpoint in this API. This is deliberate, not an oversight: Source is expected to gain new values over time (new scraped sites), while Property Type is a comparatively closed, stable set, so only Source needed a mechanism that avoids a frontend deploy per new value.
